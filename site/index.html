Spec sheet · libycxx 0.1.0

An independent C++26 standard library

An independent C++26 standard library for GCC and Clang, implemented from the working draft, with its own Itanium C++ ABI runtime. Freestanding, hosted, and available through import std;.

01

What it is

Select libycxx explicitly in place of the toolchain’s libstdc++ or libc++.

The freestanding core needs no operating system or C library. The hosted library adds streams, files, threads, clocks, and locales through a small C platform abstraction layer. Its own ABI runtime handles exceptions, RTTI, and guards; stack unwinding comes from the toolchain.

02

What is implemented

Every C++26 library header is provided, including the deprecated facilities the draft still specifies. Compiler-dependent features have known gaps.

  • Language support & utilities

    Type traits, vocabulary types, function wrappers, and constexpr exceptions on GCC.

  • Containers & ranges

    All containers, ranges, and algorithms, including <hive>, <inplace_vector>, and <mdspan>.

  • Text

    Formatting, printing, character conversion, regex, and text encodings.

  • Numerics

    Random engines and distributions, SIMD, linear algebra, and math facilities.

  • Time

    Calendars, utc/tai/gps clocks, leap seconds, and the system’s time zone database.

  • Concurrency

    Threads, atomics, synchronization, RCU, hazard pointers, and senders and receivers.

  • I/O & locales

    Streams, filesystem, standard locale facets, and named locales from the C library.

  • Diagnostics

    Stack traces, debugging, contracts, and reflection where the compiler supports them.

Freestanding builds, modules, and spec audits

Freestanding, hosted and modules

Every core header, every header with a freestanding subset and every header of the draft’s freestanding table compiles with -ffreestanding -nostdlib -nostdinc -fno-exceptions -fno-rtti; a smoke test links for x86_64-unknown-none-elf and riscv64-unknown-elf. An optional runtime archive, ycxx::freestanding, supplies allocation, floating-point <charconv> and the atomic wait tables to programs without an operating system.

The standard library modules std and std.compat are generated from the headers and built per project with the project’s own flags, from CMake (ycxx::modules) or with tools/ycxx-modules.

Audited against the draft

Three audits walk the synopses of the working draft and generate a check for every declaration, on both compilers (docs/SPEC_COVERAGE.md):

03

How it is built

A handful of rules, written down in DECISIONS.md with their reasons and the alternatives that were rejected.

How it was written

Implemented by AI agents (Claude, directed by the author) from the draft, WG21 papers, POSIX, and the Itanium ABI, without access to other implementations’ sources during development.

This is not a legal clean-room claim: the models were trained on public code. See the full account and similarity analysis.

Hidden namespaces and reserved names

Public declarations live in the inline namespace std::__y1 of std, except the few the compilers name in std itself; internals use reserved names in hidden namespaces. Argument-dependent lookup stays out of implementation details, and hidden visibility isolates runtime symbols.

Strict preprocessor policy

config.hpp turns compiler and target facts into constexpr values or types. The library uses templates, constraints, and if constexpr rather than function-like macros.

Platform layer and hosted layers

The C primitives of ycxx/pal.h have POSIX providers by default. Supply individual layers yourself to use a custom heap, console, or other environment.

Its own ABI runtime

Exceptions, RTTI, dynamic_cast, static-local guards, and handlers come from libycxx’s Itanium ABI implementation. Only stack unwinding comes from the toolchain.

Named locales on the C library

Named locales use the C library’s per-locale functions on glibc and Darwin, without changing the global C locale or other threads.

Deliberate divergences from established libraries

Deliberate divergences

Where the draft and the established libraries disagree, libycxx follows the draft and says so; where the letter of the draft would break portable code, it follows practice and says that too. The full list is in STATUS.md (“Deliberate divergences”):

  • to_chars without a precision follows P3505 and the draft’s “smallest number of characters”, where older tests encode the C++17 rule.
  • Floating-point from_chars leaves the value unmodified on result_out_of_range, as the draft says.
  • <regex>’s ECMAScript grammar follows ECMA-262 (\a is an identity escape; a back-reference may precede its group).
  • regex_traits::transform_primary in the classic locale returns the whole sort key, so [[=a=]] keeps working there, as portable code expects.
  • expected’s operator== with a value deduces its left operand, to avoid a constraint recursion the literal signature causes.
04

How it is tested

Spec-derived tests, unmodified external suites, and real-world projects check the library beyond its own implementation.

2,824 own tests and the libc++ and libstdc++ suites run with GCC and Clang. Nineteen real-world projects build against libycxx and run their own tests. CI checks Linux and macOS; nightly jobs cover additional configurations.

Failures, skips, and expected failures carry their causes. Each run writes commands, results, and transcripts in HTML and Markdown. See the testing guide for how to run the suites.

Own suite: method and results

Its own suite, written from the draft

2,824 tests in tests/ycxx, written by an author who may read only the working draft and cppreference — never libc++’s or libstdc++’s tests, nor any implementation, libycxx’s included. A failing test is a library bug until the draft shows otherwise; tests are never weakened to fit. Tests that must not compile name the diagnostic they expect, and hardened preconditions have death tests. Running the suite against libstdc++ validates the tests themselves: every difference is listed and triaged.

Sanitizers, hardening and library modes

All three suites run under AddressSanitizer, UndefinedBehaviorSanitizer and ThreadSanitizer, linked with a libycxx built with the same sanitizers — an uninstrumented library would hide every hand-off through its own mutexes and reference counts. The own suite also runs hardened, with -fno-exceptions and at -O2, each with its own report.

CI and failure policy

Continuous integration, without baselines

Every push runs the policy checks, both library builds, the freestanding check, the CMake package test and the own suite on Linux (the gcc:16 container, Clang 23 from apt.llvm.org) and macOS (Apple Silicon, Homebrew’s GCC 16, Clang 23), and on Linux a sample of both external suites. Nightly, the whole external suites run on both compilers and both platforms, with the sanitizer, hardened, no-exceptions and -O2 configurations and the real-world projects. The platform and compiler matrix lists what each combination has passed.

There is no list of tolerated failures. A test reported FAIL fails the run, and every failure is resolved where its cause is decided: a libycxx bug is fixed; a test that does not apply is skipped with its category and reason; a cause outside the test and the library — a compiler bug, an ABI limit, a draft defect — is an expected failure with its reason, and an unexpected pass fails the run so the mark goes when the cause does.

Every test, passing ones included, records its commands, exit statuses and output; each run writes an HTML report with its provenance, and a Markdown copy ready to paste to a person or an assistant.

06

Getting started

From an empty directory to import std; with libycxx, on Linux or macOS. You need git, CMake 3.28 or later, Ninja, curl and the host’s C toolchain (the Xcode Command Line Tools on macOS, build-essential or its equivalent on Linux). Nothing else has to be installed first.

It prints ["import", "modules", "std"]. The example fetches libycxx, provisions Clang 23 if needed (about a 2 GB download), and builds the modules and program. Later builds reuse the compiler cache.

The quick-start guide explains the example files, cache, and options. These commands run as written in CI.

What happens during the first build

What the commands do

  • Fetch libycxx. Before project(), CMakeLists.txt gets libycxx with FetchContent (a shallow clone of main; a release tag will replace it) and selects its toolchain file, cmake/ycxx-toolchain.cmake.
  • Provision Clang 23. The toolchain file looks for Clang 23.1 in its cache (~/.local/share/ycxx/toolchains), then on PATH and in Homebrew. When there is none, it downloads LLVM’s 23.1.2 release (a 2 GB download; Linux x86_64 and arm64, macOS on Apple silicon) into the cache, where every later project finds it.
  • Build the std modules. cmake --build compiles what hello needs from libycxx: libycxx.a, its ABI runtime, and the std and std.compat modules with the project’s own flags.
  • Build and run hello. It links libycxx and its runtime, not libstdc++ or libc++.

The first run took 3 minutes on a Linux x86_64 test machine with a fast connection: 15 seconds to download Clang, 2.5 minutes to extract it (0.8 GB of the release is kept), 20 seconds to build with 2 jobs. Later runs, and other projects, reuse the downloaded Clang.

These commands are tested as written: tests/quickstart/run.sh runs them from an empty directory against the commit under test and checks the output, with both compilers on every CI run (the cmake stage of tools/test, Linux and macOS), and with Clang downloaded into an empty cache every night (the quickstart job of the full workflow, Linux and macOS).

Use GCC instead

GCC instead of Clang

This uses GCC 16.2 when it is installed (g++-16, Homebrew’s gcc). Without one, it builds GCC from source into the cache, once, which takes about an hour on four cores; on macOS, brew install gcc first is quicker.

Existing projects

Use an installed libycxx through CMake’s find_package, its toolchain file, or compiler wrappers. Building projects covers CMake, Meson, make, autotools, Bazel, Conan, and vcpkg.

Build every C++ dependency from source against the same libycxx installation: prebuilt libstdc++ or libc++ dependencies have a different ABI. C libraries are fine.

07

Status and limitations

Every C++26 header is in place. Version 0.1.0 is still early: the ABI and implementation continue to evolve.

  • Young, without a stable ABI

    No stable ABI: rebuild your program and C++ dependencies when libycxx changes. Keep an installation per compiler.

  • C++26 only

    Older language modes are raised to C++26. Removed facilities and compiler-library extensions are not supported.

  • One runtime per image

    Shared libraries have separate runtime state. Exception state, terminate handlers, and new handlers do not cross their boundaries.

  • Compiler gaps

    Reflection and contracts need GCC support. GCC cannot mix standard header includes and import std; in one translation unit.

  • macOS is newer

    Darwin-specific facilities are less exercised. Stacktrace symbolization reads ELF/DWARF; modules are tested on Linux only.

  • Open work

    External-suite failures, missing hosted-layer primitives, and performance gaps are recorded in the status report.

STATUS.md is the full record: per-area results, known compiler gaps, the draft defects noticed along the way, and what comes next.
